# API MVP: наблюдение и подключение пациента

Префикс `/api/v1`. Время: ISO 8601 с часовым поясом, идентификаторы: UUID. Ответы JSON, кроме успешного logout (`204`). Изменяющие запросы требуют `X-Synapse-Request: 1`; при наличии `Origin` он должен входить в `ALLOWED_ORIGINS`. Браузер использует cookie с `credentials: include`.

| Метод | Путь                               | Поведение                                                                                  |
| ----- | ---------------------------------- | ------------------------------------------------------------------------------------------ |
| POST  | `/auth/login`                      | `{ email, password }` → пользователь и HttpOnly session cookie                             |
| POST  | `/auth/activate`                   | `{ code, password }` → активация подготовленного врачом аккаунта и новая сессия            |
| POST  | `/auth/logout`                     | Удаление серверной сессии и cookie                                                         |
| GET   | `/me`                              | `{ id, email, name, role }`, где role: `doctor` или `patient`                              |
| GET   | `/notifications`                   | Свои уведомления, курсорная страница и количество непрочитанных                            |
| POST  | `/notifications/{id}/read`         | Отметить собственное уведомление прочитанным; повтор сохраняет прежнее время               |
| POST  | `/notifications/read-all`          | Отметить все свои текущие уведомления прочитанными; 204                                    |
| GET   | `/patients`                        | Врач: свои пациенты, до 100; пациент: только собственный профиль                           |
| GET   | `/patients/page`                   | Поиск, статус и курсорная страница пациентов                                               |
| POST  | `/patients`                        | Врач создаёт пациента: `{ id, name, email, birth_date }`; 201 или 200 при точном повторе   |
| GET   | `/patients/{id}`                   | Карточка с последними измерениями и количеством записей                                    |
| PATCH | `/patients/{id}`                   | Только ведущий врач; обновление по ожидаемой версии, 409 при конфликте                     |
| POST  | `/patients/{id}/invitation`        | Только ведущий врач; выдаёт новый одноразовый код для ещё не активированного пациента      |
| GET   | `/patients/{id}/changes`           | Только ведущий врач; до 100 последних версий карточки с автором и значениями до/после      |
| GET   | `/patients/{id}/changes/page`      | Только ведущий врач; курсорные страницы журнала изменений без общего ограничения 100 строк |
| GET   | `/patients/{id}/diary`             | До 365 последних записей по времени измерения                                              |
| GET   | `/patients/{id}/diary/page`        | Курсорная страница дневника, до 365 записей за запрос                                      |
| GET   | `/patients/{id}/diary/{entry_id}`  | Конкретная запись этого пациента; пациент для себя или ведущий врач                        |
| POST  | `/patients/{id}/diary`             | Только пациент для себя; 201 при создании, 200 при точном повторе                          |
| GET   | `/patients/{id}/events`            | До 100 событий; пациенту доступны только опубликованные                                    |
| GET   | `/patients/{id}/events/page`       | Курсорная страница событий с серверным фильтром типа и проверкой видимости                 |
| GET   | `/patients/{id}/events/{event_id}` | Конкретное событие этого пациента; внутреннее событие пациенту не возвращается             |
| POST  | `/patients/{id}/events`            | Только ведущий врач; 201 при создании, 200 при точном повторе                              |

Пример самоотчёта:

```json
{
  "id": "d5e2e2cd-3d8a-485c-8dcb-862be7336c4a",
  "measured_at": "2026-10-24T10:00:00Z",
  "mood": 5,
  "anxiety": 4,
  "sleep_hours": 7.5,
  "comment": "Сегодня удалось хорошо выспаться"
}
```

Настроение и тревога: целые 0–10; сон: 0–24 часа; комментарий: до 2000 символов. Время не может опережать сервер более чем на 5 минут. Сервер сохраняет исходное время и время приёма отдельно. Один UUID нельзя использовать для другого содержимого (`409`), включая конкурентные повторы. Ноль — допустимое измерение.

Событие врача:

```json
{
  "id": "663cfb4e-87a2-4d7c-a183-b6b0689057fb",
  "title": "Повторная консультация",
  "body": "Обсудили записи дневника",
  "patient_visible": false,
  "kind": "consultation",
  "occurred_at": "2026-03-12T09:30:00+03:00",
  "source": "Выписка от 12.03.2026"
}
```

Заголовок после удаления крайних пробелов: 1–120 символов; текст: до 4000; источник: до 500 символов. `source` необязателен, пустое значение нормализуется в `null`. Тип `kind`: `initial_assessment`, `consultation`, `plan_change`, `note`, `other`; по умолчанию `note`. Тип «изменение плана» описывает событие истории и не создаёт назначения лекарств.

`occurred_at` — необязательные дата и время с часовым поясом. Если поле отсутствует или равно `null`, сервер назначает время первой записи. При явной дате допускаются события до начала наблюдения, но не раньше даты рождения (календарная дата входного часового пояса) и не более чем на 5 минут позже серверного времени. В БД время сохраняется как UTC-момент. Клиент передаёт смещение выбранной даты, включая историческое летнее время.

Список возвращает `id`, `title`, `body`, `patient_visible`, `kind`, `source`, `occurred_at`, `created_at`, `author_name`. `created_at` и автор назначаются сервером и не меняются при повторе. Сортировка: дата события, время внесения, UUID — по убыванию; максимум 100 записей. Пациент получает только опубликованные события, включая их источник; внутренние тексты и источники не возвращаются ему.

Одинаковый повтор UUID возвращает 200, первоначальное создание — 201. Изменение даты, типа, источника, текста или видимости с тем же UUID даёт 409. Замена явно заданной даты на отсутствие даты тоже даёт конфликт. Старые клиенты без новых полей поддерживаются: повтор не меняет время исходного события. Редактирование и удаление событий не реализованы.

Для критического алерта ведущий врач отдельно сохраняет решение о маршрутизации через `POST /patients/{id}/alerts/{alert_id}/routing`. Категория принимает значения `mandatory`, `preferred` или `not_indicated`; требуется обоснование и актуальная версия алерта. Это подтверждённое врачом решение, а не автоматическое направление. Пациент получает только сохранённую категорию и обоснование.

Список `GET /alerts` принимает курсор `before` + `before_id` и фильтр `status`: `new`, `acknowledged`, `resolved` или `active`. Значение `active` возвращает только алерты со статусом `new` и `acknowledged`, сохраняя курсорную пагинацию. Главная врача запрашивает активную очередь; обработанные алерты остаются доступны в истории конкретного пациента.

Доменная ошибка: `{ "error": { "code": "forbidden", "message": "Нет доступа к этим данным" } }`.

Основные статусы: `401` — нет сессии/неверные учётные данные; `403` — нет доступа/защита запроса; `409` — конфликт UUID; `422` — неверные значения; `429` — более 20 попыток входа в минуту с одного IP; `500` — внутренняя ошибка. Ошибки формата JSON, UUID и лимита тела пока могут возвращаться стандартным текстовым ответом Axum; frontend обрабатывает их без предположения о JSON.

## Карточка и подключение

Ответ карточки дополнен `email`, `account_activated` и `version`. Новый аккаунт создаётся с `account_activated=false` и недоступен для входа до принятия кода. Создание пациента и начального события выполняется одной транзакцией. Почта нормализуется в нижний регистр; совпадение уже занятого логина возвращает 409 `account_exists`. Точный повтор создания по тому же UUID не создаёт новый аккаунт или событие.

Приглашение: `{ code, expires_at }`. Код из 64 шестнадцатеричных символов возвращается только при выдаче, в БД хранится SHA-256. Срок — 72 часа. Новый код отзывает предыдущий; активированному пациенту выдать код повторно нельзя. Неправильный, отозванный, использованный или просроченный код даёт 422 с общим сообщением. Новый пароль: 8–128 символов, не только пробелы. Активация аккаунта, использование кода и создание сессии фиксируются одной транзакцией. Для входа и активации отдельно действует ограничение 20 запросов в минуту с одного IP.

Пример PATCH (все перечисленные поля обязательны):

```json
{
  "version": 1,
  "name": "Анна Петрова",
  "birth_date": "1998-04-12",
  "observation_started": "2026-10-24",
  "status": "active",
  "medical_summary": "Сведения наблюдения",
  "allergies": null
}
```

Статусы: `active`, `observation`, `archived`. Имя — до 120 символов; дата рождения — с 1900 года до текущей даты; начало наблюдения — между рождением и текущей датой. Медицинские сведения — до 6000 символов, аллергии — до 2000. Пустое поле аллергий нормализуется в `null` («нет сведений»), а не в подтверждение отсутствия аллергий.

Успех возвращает полную карточку с увеличенной версией. Если значения не менялись, версия и аудит не увеличиваются. Несовпадение версии возвращает 409 `stale_version`; текущая карточка не перезаписывается. Изменение профиля и запись аудита атомарны. Успешный повтор старого PATCH возвращает конфликт версии: для продолжения нужно перечитать карточку, без автоматического повторного применения изменений.

Журнал содержит `id`, `author_name`, `created_at`, `version_before`, `version_after`, `before_data`, `after_data`. Поля до/после включают редактируемые сведения и версию; секретов аккаунта в журнале нет. Сведения текущей карточки доступны пациенту; журнал предыдущих значений — только ведущему врачу.

`GET /health`: процесс отвечает. `GET /ready`: выполняет запрос к БД, возвращает 503 при её недоступности. Ответы API получают `X-Request-Id`.

Машиночитаемый контракт — `contracts/openapi.json`, автоматически генерируемый из серверных типов и того же реестра, который регистрирует маршруты Axum. TypeScript-типы и операции клиента строятся из этого документа; проверка `npm run api:check` обнаруживает расхождения. Этот файл дополняет схему бизнес-правилами. Инструкции — в `contracts/README.md`. Основные списки интерфейса имеют курсорные страницы; старые методы-массивы сохранены для совместимости.

## Центр уведомлений

`GET /notifications` принимает `limit` (1–50, по умолчанию 20). Следующая страница задаётся парой `before` (ISO 8601) и `before_id` (UUID), взятой из `next_cursor`; передавать только часть курсора нельзя. Сортировка: `created_at DESC, id DESC`. Курсор не зависит от отметок прочтения и не сдвигается при добавлении более новых уведомлений.

Ответ: `{ items, unread_count, next_cursor }`. `next_cursor` равен `null` на последней странице. `unread_count` — общее количество непрочитанных уведомлений текущего пользователя. Элемент содержит `id`, `patient_id`, `patient_name`, `kind`, `related_id`, `created_at`, `read_at`. Типы: `diary_entry` — запись дневника для ведущего врача; `published_event` — опубликованное событие для пациента. Тексты дневника, события и его источник в уведомление не копируются.

Уведомление создаётся в транзакции с новой исходной записью. Точный повтор исходного UUID не создаёт ещё одно уведомление; конфликтный повтор откатывает транзакцию. Внутреннее событие врача не создаёт уведомление пациенту. Для чата уведомление `chat_message` получает противоположная сторона диалога и не содержит медицинского текста; переход открывает раздел сообщений. Старые записи не превращаются в фиктивные новые уведомления при миграции.

Все операции определяют получателя по серверной сессии, параметра выбора получателя нет. Попытка отметить чужой или отсутствующий UUID возвращает одинаковый 404 `not_found`. `POST /notifications/{id}/read` возвращает `{ read_at }`, повтор не меняет время прочтения. `POST /notifications/read-all` затрагивает только уведомления текущего пользователя. Оба метода требуют обычной защиты изменяющих запросов.

В Tauri query-параметры передаются отдельно в `api_request.query` как объект строк и кодируются Rust-клиентом. Произвольный URL, cookie и заголовки из WebView по-прежнему не принимаются. Путь команды не включает query-строку. Журнал изменений карточки также поддерживает курсорные страницы, описанные ниже.

При переходе из уведомления клиент загружает историю пациента и, если связанной записи нет в странице, получает её отдельным GET по UUID. Для обоих новых методов сначала проверяется доступ к пациенту, затем принадлежность записи именно этому пациенту. Отсутствующая или не видимая пациенту запись возвращает одинаковый 404 `not_found`. Подстановка UUID чужой записи не обходит проверку доступа. Дневник, события и журнал изменений дополнительно поддерживают курсорные страницы; прежние методы без `/page` сохраняют старые ограничения для совместимости.

## Сообщения врача и пациента

`GET /patients/{id}/messages` возвращает `{ items, unread_count, next_cursor }`. Сообщения принадлежат одному наблюдению и доступны только пациенту либо его ведущему врачу; сервер не принимает получателя из запроса. Курсор использует пару `before` и `before_id`, сортировка — от новых к старым, размер страницы — 50.

`POST /patients/{id}/messages` принимает `{ client_id, body }`. Текст ограничен 4000 символами и сохраняется до подтверждения доставки. Повтор с тем же `client_id` и теми же автором, пациентом и текстом возвращает исходную запись; повтор с изменённым содержимым даёт 409 и не перезаписывает историю. Новое сообщение и in-app уведомление второй стороне создаются атомарно. `POST /patients/{id}/messages/read` отмечает прочитанными только входящие сообщения текущего пользователя и возвращает число изменённых записей. Вложения, push и системное уведомление с текстом сообщения в MVP не входят.

## Приёмы и простое расписание

`GET /appointments` возвращает свободные и назначенные интервалы текущего врача или пациента в указанном периоде. Врач создаёт интервал через `POST /appointments`, передавая `client_id`, начало, окончание и необязательного пациента. Пациент бронирует свободный интервал через `POST /appointments/{id}/book` с собственным `client_id`. Сервер проверяет принадлежность ведущему врачу, запрещает прошлые интервалы и сериализует пересечения advisory lock врача. Повтор бронирования с тем же идентификатором идемпотентен, занятый слот возвращает 409. Назначение или бронирование создаёт второй стороне уведомление `appointment` без медицинского текста в той же транзакции.

`POST /appointments/{id}/cancel` отменяет свободный или назначенный интервал для его врача либо пациента, указанного в записи. `POST /appointments/{id}/reschedule` доступен врачу и изменяет время с проверкой пересечений. Оба запроса принимают `expected_version`; устаревшая версия возвращает 409 и не создаёт уведомление. Перенос и отмена увеличивают версию, а уведомление второй стороне создаётся в той же транзакции.

## Страницы пациентов

`GET /api/v1/patients/page` возвращает `{ items, total_count, matching_count, next_cursor }`. `items` содержит карточки; `total_count` — всех доступных текущей роли пациентов, `matching_count` — число совпадений поиска и статуса до применения курсора. Врач получает только своих пациентов, пациент — только себя.

Параметры: `search` — буквальная подстрока имени без учёта регистра (после удаления крайних пробелов до 120 символов, без управляющих символов); `status` — `all`, `active`, `observation` или `archived`; `limit` — 1–50, по умолчанию 20. Символы `%`, `_` и обратная косая черта ищутся буквально.

Сортировка: `name ASC, id ASC`. `next_cursor` — `{ name, id }` либо `null` на последней странице. Следующий запрос передаёт оба значения как `before_name` и `before_id`, сохраняя поиск и статус. Несмотря на имя параметров, следующая страница идёт после указанной пары в порядке сортировки. UUID разрешает совпадения имён без пропуска строк. При смене поиска или статуса клиент сбрасывает курсор. Неполный курсор, неизвестный статус и недопустимый размер страницы дают 422.

Прежний `GET /api/v1/patients` сохранён для совместимости: массив максимум из 100 карточек. SPA использует `/patients/page`; начальная загрузка содержит до 50 карточек, каталог загружает страницы по 20 и получает выбранную карточку отдельно, если её нет в начальной странице.

## Страницы дневника и событий

`GET /patients/{id}/diary/page` и `GET /patients/{id}/events/page` возвращают `{ items, next_cursor }`. Проверки сессии и доступа к пациенту совпадают с обычным чтением карточки. Пациент получает только опубликованные события; приватные записи исключаются до ограничения страницы.

`limit` по умолчанию 50; для событий допустимо 1–50, для дневника 1–365. События поддерживают `kind`: `all`, `initial_assessment`, `consultation`, `plan_change`, `note`, `other`. Фильтр действует по всей истории; при его изменении курсор сбрасывается. Дневник не принимает `kind`.

`next_cursor` — `{ before, before_created, before_id }`, где `before` — время измерения либо события, `before_created` — время внесения, `before_id` — UUID. Все три поля передаются query-параметрами следующего запроса без изменения. На последней странице курсор равен `null`. Порядок — время измерения/события, время внесения и UUID, всё по убыванию. Совпадения дат не теряют строки; добавление более новой записи не сдвигает уже полученный курсор. Это не снимок БД: внесённая задним числом запись может появиться на последующих страницах или после обновления.

Неполный курсор, неизвестный тип и недопустимый лимит дают 422. Синтаксически неверные даты/UUID/числа query могут давать стандартный текстовый ответ Axum 400. Старые GET без `/page` сохранены для совместимости с прежними ограничениями.

SPA сначала загружает 365 измерений для существующих графиков и 50 событий. Следующие страницы дневника — по 50; события — по 50. Обновление заново получает первые страницы; фильтр текущего пациента сохраняется. На графиках отображаются загруженные измерения выбранного периода; при наличии старых страниц интерфейс сообщает об этом. Запись, открытая отдельно из уведомления, не сдвигает курсор и не дублируется при последующей загрузке страницы.

## Страницы журнала изменений карточки

`GET /patients/{id}/changes/page` возвращает `{ items, next_cursor }`. Элементы имеют тот же формат `ProfileChange`, что и прежний `/changes`: автор, дата внесения, версии и значения до/после. Доступ разрешён только ведущему врачу; пациент не получает даже собственный журнал. Все страницы повторяют серверную проверку сессии, роли и связи врача с пациентом.

`limit`: 1–50, по умолчанию 20. Порядок: `version_after DESC`. `next_cursor` — `{ before_version }` либо `null` на последней странице; следующая страница передаёт `before_version` без изменения и возвращает строго меньшие версии. Номер версии уникален в карточке, поэтому дата или UUID для разрешения совпадений не требуются. Используется существующий уникальный индекс `(patient_id, version_after)`; новая миграция не нужна.

`before_version` — целое число не меньше 2. Запрос с `before_version=2` возвращает пустую последнюю страницу. Недопустимые диапазоны дают 422, синтаксически неверное либо выходящее за i32 значение query — стандартный ответ Axum 400. Новое изменение после получения курсора не сдвигает старые страницы. Неизменившийся PATCH не создаёт версию или строку аудита.

SPA загружает страницы по 20. Пока идёт запрос, повторная загрузка заблокирована. При ошибке уже прочитанные версии сохраняются, а ту же страницу можно запросить повторно. Переключение пациента и обновление заново получают первую страницу; поздний ответ старого пациента игнорируется. Прежний `/changes` сохранён как массив до 100 строк для совместимости.

## Структурированные диагнозы

Врач сначала выбирает проявления, затем вручную назначает диагноз. Каталог не выполняет диагностический алгоритм. Все адреса ниже имеют префикс `/api/v1`.

| Операция                                              | Доступ и результат                                                             |
| ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| GET `/clinical/findings`                              | Только врач: поиск по общему списку пунктов источника, контекст и страницы PDF |
| GET `/clinical/diagnosis-catalog`                     | Только врач: ручной поиск записываемого кода                                   |
| GET `/clinical/source/{code}`                         | Только врач: исходный раздел для проверки критериев                            |
| GET `/clinical/drugs`                                 | Только врач: активные опубликованные препараты и их структурированные сведения |
| GET `/patients/{id}/diagnoses`                        | Ведущий врач или сам пациент: записи с выбранными пунктами                     |
| GET `/patients/{id}/diagnoses/{diagnosis_id}`         | Те же права, запись должна принадлежать указанному пациенту                    |
| POST `/patients/{id}/diagnoses`                       | Ведущий врач: создание с клиентским UUID                                       |
| PATCH `/patients/{id}/diagnoses/{diagnosis_id}`       | Ведущий врач: изменение ожидаемой версии                                       |
| GET `/patients/{id}/diagnoses/{diagnosis_id}/changes` | Только ведущий врач: сохранённые версии и автор                                |

Точные DTO и имена операций генерируются в OpenAPI. Каталоги используют `search`, `offset`, `limit` (по умолчанию 20, максимум 50), возвращают `total`, `next_offset` и версию источника. Пациенту запрещены и каталоги, и исходные разделы, и справка, и аудит, даже при прямом запросе API.

Тело сохранения: `id`, `version`, `catalog_version`, `code`, `finding_ids`, `diagnosed_on`, `status` (`active` или `resolved`), `note`. При создании версия равна 1; в PATCH UUID должен совпадать с адресом. Нужно от 1 до 100 различных известных пунктов и существующий записываемый код. Дата ограничена датой рождения и текущим днём, комментарий — 4000 символами и явно виден пациенту. Название диагноза и подписи пунктов сервер берёт из каталога, а не из пользовательского текста.

В записи сохраняются версия каталога и снимки выбранных пунктов: идентификатор, подпись, код источника, страница PDF. Общий список и контекст не входят в ответ с диагнозом. Обновление каталога не меняет старые снимки. Несовпадение версии каталога даёт 409 `catalog_changed`; старая версия записи — 409 `stale_version`. Сначала нужно загрузить актуальную запись; несохранённые изменения не применяются автоматически.

Повтор идентичного POST с тем же UUID возвращает существующую запись без дубля. PATCH без изменений не повышает версию. Изменение и снимок аудита сохраняются одной транзакцией; параллельные запросы сериализуются. Удаление не предусмотрено, завершённый диагноз получает `resolved`. Список записей использует курсор по дате создания и UUID, аудит — `before_version`. Список диагнозов: по умолчанию 20, максимум 50; аудит: фиксированные страницы по 20. Каждая страница повторно проверяет права.

Происхождение источников, версия импорта и ограничения справки описаны в `clinical/README.md`.

## Структурированный анамнез

`Patient.medical_history` — обязательный объект в GET карточки и списках пациентов. Поля: `complaints` (жалобы), `present_illness` (история текущего состояния), `life_history` (анамнез жизни), `comorbidities_status`, `comorbidities_details`. Все текстовые поля — строки, по 6000 символов максимум; сервер обрезает пробелы по краям. Переносы строк и табуляция допустимы, прочие управляющие символы отклоняются. Пустое поле означает отсутствие сведений.

Состояния сопутствующих состояний:

| Значение  | Смысл                                  | Описание                       |
| --------- | -------------------------------------- | ------------------------------ |
| `unknown` | Нет сведений                           | Только пустая строка           |
| `none`    | Врач указал, что состояния не выявлены | Только пустая строка           |
| `present` | Есть сведения                          | Обязательное непустое описание |

Новая миграция 0007 добавляет объект со статусом `unknown` и пустыми полями для существующих карточек. Она не выводит анамнез из старого свободного текста и не объявляет отсутствие заболеваний автоматически.

Сохранение выполняется существующим PATCH `/patients/{id}` с ожидаемой версией. Ведущий врач может изменить блок, пациент — только прочитать. Комментарий формы прямо сообщает, что сведения видны пациенту; для внутренних записей остаётся отдельная заметка врача. Новый интерфейс передаёт весь объект. Отсутствующий или `null` блок от старого клиента сохраняет текущий анамнез. Чтобы очистить сведения, нужно передать объект с пустыми текстами и статусом `unknown`.

Анамнез входит в сравнение изменений, общую версию и атомарный журнал карточки. Неизменённый PATCH не создаёт версию; конкурентное изменение возвращает 409 `stale_version`. Старые снимки журнала без блока остаются допустимыми; интерфейс отображает отсутствие данных, не переписывая историю. Пациенту журнал запрещён. Серверный общий лимит JSON-тела увеличен до 256 КиБ для нескольких полей Unicode и JSON-экранирования; большие тела отклоняются с 413, ограничения отдельных полей сохранены.

## Регистрация и приглашения по макету

POST `/auth/register` (`register`) принимает `email` (сохранённое имя поля для телефона или почты), `first_name`, `last_name`, `password`, `password_confirmation`, `consent`. Создаётся только роль patient, возвращаются 201 и cookie-сессия; роль из пользовательского тела не применяется. Согласие и совпадение паролей обязательны; время согласия сохраняется в users. Занятый логин даёт 409. Регистрация не создаёт фиктивную дату рождения, не назначает врача и не открывает имеющуюся карточку.

Номера принимаются в международном формате `+` и 10–15 цифр. Пробелы, скобки и дефисы номера удаляются одинаково при входе, регистрации и создании пациента врачом. Почта обрезается по краям и приводится к нижнему регистру. Контакты не обозначаются подтверждёнными.

GET `/auth/invitation/{code}` (`invitation_preview`) по действующему секретному токену возвращает только имя врача и признак существующего аккаунта; недействительное/отозванное/принятое/просроченное приглашение — 404. Ограничивается частота запросов. Токен передаётся ссылкой в `#invite=...`, а не ручным полем. В пользовательском интерфейсе новые приглашения заменяют прежнюю выдачу кода.

Существующий POST `/auth/activate` сохранён. Для нового аккаунта пароль устанавливается, для уже зарегистрированного — проверяется и сохраняется прежним. Подтверждение связи `access_accepted` и расходование токена происходят атомарно с созданием сессии. Повторное применение запрещено. Публичный просмотр карточки, страницы списков и уведомления наблюдения недоступны до принятия.

Если врач создаёт приглашение для самостоятельно зарегистрированного пациента без наблюдения, используется канонический UUID существующего аккаунта. Ответ `/patients` возвращает этот UUID; он может отличаться от нового клиентского UUID запроса. Повтор до принятия не создаёт дубликат. Существующее наблюдение другого врача не перепривязывается. Поле `account_activated` в карточке означает, что аккаунт активен и связь наблюдения принята.

## Основная информация медкарты

`Patient.physical_info` — обязательный объект с nullable `height_cm`, `weight_kg`, `blood_group`. В PATCH это необязательный блок: отсутствие/null сохраняет текущие сведения, явные null внутри объекта очищают соответствующие значения. Рост и вес — положительные конечные числа до 400 см и 1000 кг; группа крови — один из восьми вариантов ABO/Rh. Неизвестное не заменяется данными макета. Изменения входят в версию и аудит карточки. Возраст вычисляется из даты рождения, десятичные значения отображаются в русской локали.

## Опросники GAD‑7

Все адреса имеют префикс `/api/v1`. Источники и условия выбранной русской адаптации описаны в `clinical/README.md`.

| Метод                                               | Операция                   | Права                                          |
| --------------------------------------------------- | -------------------------- | ---------------------------------------------- |
| GET `/questionnaires/gad7`                          | `questionnaire_definition` | Только врач, текущая проверенная версия        |
| GET `/patients/{id}/questionnaires`                 | `list_questionnaires`      | Ведущий врач или сам пациент с принятой связью |
| POST `/patients/{id}/questionnaires`                | `assign_questionnaire`     | Только ведущий врач                            |
| GET `/patients/{id}/questionnaires/{assignment_id}` | `get_questionnaire`        | Ведущий врач или сам пациент                   |
| POST `.../{assignment_id}/submit`                   | `submit_questionnaire`     | Только сам пациент                             |
| POST `.../{assignment_id}/cancel`                   | `cancel_questionnaire`     | Только ведущий врач                            |
| GET `.../{assignment_id}/changes`                   | `questionnaire_changes`    | Только ведущий врач                            |

Назначение принимает `{ id, scale_version, note }`: UUID стабилен при повторе, версия должна быть известной текущей, комментарий виден пациенту и ограничен 2000 символами. Возраст проверяется сервером при назначении и отправке: эта версия для взрослых от 18 лет. Полная форма сохраняется снимком в каждой записи. Статусы: `assigned`, `completed`, `cancelled`. Одновременно разрешено одно незавершённое назначение GAD‑7 пациенту; повторные измерения создаются после завершения или отмены.

Точный повтор POST возвращает тот же UUID без новой строки аудита (201 при создании, затем 200). Отправка принимает `{ version, scale_version, answers }`: ровно семь целых значений 0–3. Клиентский score не используется. Сервер вычисляет балл, категорию, дату завершения и повышает версию с 1 до 2 одной транзакцией вместе с аудитом. Одинаковый повтор исходной отправки возвращает сохранённый результат. Изменить ответы завершённого опросника нельзя; для повторной оценки требуется новое назначение. Другая версия формы или конфликт состояния дают 409.

Отмена принимает `{ version }`. Она доступна лишь до завершения, повтор отмены той же исходной версии не создаёт второй переход. Отмена и отправка сериализуются в том же порядке блокировок пользователя и записи; при гонке только одно действие завершается успешно, другое получает 409. Удаления и повторного открытия нет. Аудит содержит автора, время, действие и полный снимок; жизненный цикл текущей записи ограничен двумя версиями, поэтому журнал возвращается целиком.

Список: `limit` 1–50 (по умолчанию 20), фильтр `status` из трёх состояний, полный курсор `before` + `before_id`. Порядок по времени создания и UUID, каждая страница заново проверяет доступ. График строится отдельно от дневника по времени завершения загруженных результатов; разные версии форм не объединяются в одну линию. Поздние ответы старого пациента или устаревшего запроса игнорируются.

Новые назначения и результаты доступны при открытии раздела и обновлении данных; отдельная доставка уведомлений об опросниках пока не подключена. Результат не создаёт диагноз, лекарственное назначение или алерт автоматически.

### Каталог опубликованных опросников

`GET /questionnaires/catalog` доступен врачу и возвращает активные формы для назначения. В карточке пациента врач выбирает форму по списку или поиску, затем создаёт назначение через `POST /patients/{id}/custom-questionnaires` с `{ id, form_id, note }`. Пациент получает только назначенную ему форму и её вопросы, не полный каталог. Отправка идёт через `POST /patients/{id}/custom-questionnaires/{assignment_id}/submit` с `{ version, answers }`; сервер проверяет диапазоны, считает сумму и категорию по снимку версии.

PHQ‑9 поставляется как встроенная неизменяемая форма. При любом ответе выше нуля на девятый вопрос сервер в транзакции завершения создаёт врачу критический алерт `phq9_positive_item_9_review`. Пациенту показывается сообщение, что ответ передан врачу для личной оценки, и инструкция обратиться в местную экстренную службу, если он сейчас не может оставаться в безопасности. Это уведомление не устанавливает диагноз и не определяет автоматически срочность.

## Терапия, приверженность и нежелательные явления

Все адреса ниже имеют префикс `/api/v1`. Полные DTO генерируются в OpenAPI.

| Метод и путь                                           | Операция                                      | Доступ                                                        |
| ------------------------------------------------------ | --------------------------------------------- | ------------------------------------------------------------- |
| GET/POST `/patients/{id}/prescriptions`                | `list_prescriptions`, `create_prescription`   | Ведущий врач создаёт; пациент читает только нечерновые записи |
| PATCH `/patients/{id}/prescriptions/{prescription_id}` | `update_prescription`                         | Только ведущий врач, ожидаемая версия                         |
| POST `.../publish`, POST `.../cancel`                  | `publish_prescription`, `cancel_prescription` | Только ведущий врач                                           |
| GET `.../changes`                                      | `prescription_changes`                        | Только ведущий врач                                           |
| POST `.../marks`                                       | `record_adherence`                            | Только сам пациент                                            |
| GET `.../adherence`                                    | `prescription_adherence`                      | Ведущий врач или сам пациент                                  |
| GET/POST `/patients/{id}/adverse-events`               | `list_adverse_events`, `record_adverse_effects` | Читают обе стороны; создаёт только ведущий врач              |
| POST `/patients/{id}/adverse-events/{event_id}/review` | `review_adverse_event`                        | Только ведущий врач                                           |

Создание назначения принимает клиентский UUID, версию 1, идентификатор активного диагноза пациента, код препарата и SHA-256 его активной серверной справки, дозировку, от одного до шести уникальных времён `ЧЧ:ММ`, даты и инструкции. Код лекарства должен входить в связи с диагнозами опубликованной версии препарата. Сервер сохраняет неизменяемые снимки диагноза и справки. Одновременно допускается один черновик или одно действующее назначение одного препарата пациенту. Точный повтор UUID идемпотентен; другое содержимое или устаревшая версия дают 409.

Черновик пациенту не возвращается. Публикация переводит его в `active`, создаёт версию аудита и уведомление пациенту в одной транзакции. Изменение разрешено для черновика и действующей записи, отмена — отдельный переход `cancelled`; удаление не предусмотрено. Аудит доступен только ведущему врачу.

Отметка приёма относится к одной дате и одному времени опубликованной активной схемы. На один запланированный приём допускается одна неизменяемая отметка `taken` либо `skipped`; повтор идентичного UUID идемпотентен. Сводка принимает `from` и `to` с периодом не более 367 дней, возвращает ожидаемое число приёмов, принятые, пропущенные, неотмеченные и процент `taken / expected`. Ожидаемый период ограничивается текущей датой, датой окончания или отмены; в текущую дату учитываются все времена схемы.

Выявленную реакцию фиксирует только ведущий врач после опроса пациента: выраженность `mild`, `moderate` или `severe`, время, пункты из сохранённого снимка назначенного препарата и необязательная заметка врача. Сервер отклоняет пункты вне справки. Запись видна пациенту в истории, но не создаёт уведомление или автоматический критический алерт и не изменяет назначение. Исторические записи прежнего формата сохраняются; их разбор доступен врачу.


Назначения: новый запрос обязан содержать diagnosis_id, drug_code и SHA-256 активной справки. Сервер принимает только активный диагноз этого пациента и препарат, связанный с кодом диагноза в опубликованной администратором версии. Для врача доступен список активных препаратов; пациентский API не раскрывает общий каталог. В назначении сохраняются снимки диагноза и справки. Старые назначения после миграции могут иметь diagnosis_id = null и остаются историческими.
